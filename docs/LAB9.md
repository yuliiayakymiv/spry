# Lab 9 — One project, two clouds: Spry on Google Cloud

Spry's core (frontend, API, database) runs on Google Cloud next to the AWS stack. Service choices:
[ADR 0008](adr/0008-google-cloud.md). Infrastructure: [`gcp/`](../gcp/) (own state in a
versioned Cloud Storage bucket, ADR 0008), application road: [`gcp/deploy.sh`](../gcp/deploy.sh). How to run and stop it:
[gcp/README.md](../gcp/README.md).

```
Browser ──▶ Firebase Hosting  https://<project>.web.app   (static site, CDN, HTTPS)
               └─ /api/** rewrite ──▶ Cloud Run  spry-api  (same Docker image as on AWS, as spry-api@)
                                         ├─ Secret Manager: DATABASE_URL (password generated by Terraform)
                                         └─ Cloud SQL connector ──▶ Cloud SQL PostgreSQL 17, db-f1-micro
Sign-in: Cognito on AWS (eu-central-1). The API verifies its JWTs itself.
Weekly report, agenda parser, e-mail (SES): still on AWS.
```

## Part 3 — the minimal setup on both clouds, and what it costs

List prices in USD, 730 h/month, no tax, checked 2026-11-05. AWS: us-east-1 (as Lab 4); Google
Cloud: europe-west1, which for Cloud SQL Enterprise and Cloud Run is priced like us-central1
(db-f1-micro ≈ $0.0105/h). Free-tier assumptions are stated per line; the trial's $300 credit is
**not** counted (it expires, the architecture does not).

at the price of rewriting the data layer (ADR 0008).

### The four traffic profiles (Lab 4)

Assumptions: demos 10 × 2 h; office hours 8 h × 22 days = 176 h; busy = ~1 request/s around the
clock (2.6 M requests, 100 ms each, ~5 DB reads per request). Aurora at 0.5 ACU ($0.06/h) while
awake; Cloud SQL "stopped" = started only for the profile's hours.

| Profile | AWS real stack (Fargate + ALB + RDS) | AWS Stage 2 (Lambda + Aurora) | GCP Cloud SQL 24/7 | GCP Cloud SQL started only when used | GCP Firestore |
|---|---|---|---|---|---|
| Nobody | $52 | **$0.30** | $9.40 | $1.70 | **$0** |
| Class demos (20 h) | $52 | **$1.30** | $9.40 | $1.90 | **$0** |
| Office hours (176 h) | $52 | $10.70 | $9.40 | $3.55 | **$0** |
| Busy 24/7 (730 h) | $53 | $46 (1 ACU: $90) | **$11.60** | $11.60 | $5.70 |

Line by line for *busy* on GCP: Cloud SQL $9.37; Cloud Run 2.6 M requests (−2 M free) × $0.40/M =
$0.24, 260 k vCPU-s (−180 k free) × $0.000024 = $1.92, memory within the free 360 k GiB-s.
Firestore: 13 M reads (−1.5 M free) × $0.03 / 100 k = $3.45.

**Which cloud is cheaper, and which single line decides it**

- **Nobody, class demos:** AWS Stage 2 ($0.30 / $1.30) beats GCP with Cloud SQL ($9.40). The line
  is **database compute**: Aurora pauses to 0 ACU, Cloud SQL bills every hour it runs. With
  Firestore GCP is $0 and wins.
- **Office hours:** about a draw ($10.70 vs $9.40), GCP slightly cheaper — Aurora is awake 176 h
  at $0.06, Cloud SQL 730 h at $0.0105: the hourly *rate* decides (Aurora's ACU-hour is ~6× dearer).
- **Busy 24/7:** GCP ($11.60) is ~4× cheaper than Aurora ($46). Same line, database compute:
  a running f1-micro costs far less than an awake Aurora.
- **Against our real AWS stack** (Fargate + ALB + RDS, $52 whatever the traffic) GCP is cheaper in
  every profile. The lines that decide it are the **ALB ($16.43) and the 3 public IPv4 ($10.95)**:
  Cloud Run and Firebase include the HTTPS endpoint, so there is no load balancer and no address to
  rent.

**Where is the equivalent of Lab 4's Aurora trap on the GCP side?**

Lab 4: something that keeps Aurora awake (a 1-minute health check running `SELECT 1`) makes
"serverless" dearer than an instance. On GCP the database cannot be kept awake — it never sleeps —
so the trap moves to **Cloud Run**: `min_instance_count = 1` or *CPU always allocated*
(instance-based billing) turns a $0 API into one that bills 24/7 (1 vCPU + 512 MiB ≈ $45/month,
more than the database). A startup probe or an uptime check alone does not do it, the settings do.
The second trap is **Firestore's per-read bill**: a list page that reads 500 documents per visit
spends the daily 50 k free reads after 100 visits — the bill follows the code, as Aurora's followed
the health check. And the classic one: a **stopped Cloud SQL still bills its storage**, and a
forgotten running one bills ~$0.30/day — the most common surprise on a student's bill.

## Part 4 — demos

| Demo | Result |
|---|---|
| **BigQuery** over `bigquery-public-data.usa_names.usa_1910_current`: top names of the 2010s | 10 rows (Emma, Olivia, Noah, Sophia, Liam, …), **161.77 MB processed**, 162 MB billed, 0.66 s — 0.02 % of the free TiB a month |
| **Looker Studio** over that query (BigQuery → *Open in* → Looker Studio) | report "Lab 9 - Spry - BigQuery: top names of the 2010s": table + bar chart of births per name |
| **Vision API OCR** (`gcloud ml vision detect-document`) on a handwritten sample page | "This is a hand written message to use with Google Cloud Platform, To demonstrate the capabilities of the Cloud Vision API to detect handwritten text," — word for word; 1 unit of the 1 000 free a month |

**Document AI vs a general LLM (Lab 6).** A specialised service wins when the input is a *document*
(scans, photos, forms, tables) and the output is fixed: it is cheap ($1.50 / 1 000 pages, 1 000
free), deterministic, gives coordinates and confidence per word, and does not hallucinate a field
that is not there. An LLM wins when the input is free text and the output needs understanding —
Lab 6's agenda pasted from an e-mail, with times implied ("after lunch") and items to merge. Often
both: OCR first, LLM on the text.

**Lab 8 on Google Cloud.** Athena + Glue Catalog + the CTAS to Parquet → **BigQuery** (load the JSON
once into a native, columnar table; no partitions to register, no crawler, no separate
JSON/Parquet copies to keep in sync); the stream (Kinesis/SQS → Lambda → S3) → **Pub/Sub →
Dataflow** (one Beam job for the stream *and* the replay, with event-time windows and watermarks
built in — what our `consumer.py` did by hand) **→ BigQuery**; QuickSight → **Looker Studio**
(free). No longer managed by us: the Glue catalog and `MSCK REPAIR`, the Parquet rewrite, the
watermark and dedup code, and the Lambda batching.

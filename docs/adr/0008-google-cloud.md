# ADR 0008 — Spry's core on Google Cloud: service choices

- Status: accepted
- Date: 2026-11-05
- Lab: 9 (One project, two clouds)

## Context

Spry runs on AWS (eu-central-1): frontend on S3 + CloudFront, API (FastAPI) as a container on
ECS Fargate behind an ALB with RDS PostgreSQL (Lab 2 stack), sign-in with Cognito + Google
(Lab 4), the weekly report (Lab 5: EventBridge Scheduler → SQS → Lambda → S3 → SES), the agenda
parser (Lab 6: Lambda + Bedrock/Nova), all of it in Terraform with state in HCP Terraform (Lab 7).
The question: what does it take to run the same system on Google Cloud, and what does it cost?
The lab moves the **core** (frontend, API, database); the rest is a stretch.

Constraints that decide most rows: NFR-7 (personal data stays in the EU), NFR-8 (cheap per member),
NFR-12 (4 engineers, no ops person → managed services), and "no long-lived keys".

## Decision — row by row

| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront + WAF, static frontend | **Firebase Hosting** | **replace** | CDN + managed HTTPS on `<project>.web.app` included, free plan (10 GB stored, 360 MB/day out). `/api/**` is rewritten to Cloud Run → one origin, no CORS, as CloudFront did. A bare Cloud Storage bucket has no HTTPS on a domain without a load balancer billed by the hour. |
| ECS Fargate + ALB (Lab 2) | **Cloud Run** | **replace** | The same Docker image runs (no Lambda adapter, never had one: our API is a container); Cloud Run sends HTTP to `$PORT`. Scales to zero, HTTPS URL included, no ALB and no public IPv4 to pay for. Min 0 / max 2 instances. |
| ECR | **Artifact Registry** | replace | 0.5 GB free; cleanup policy keeps the last 3 images. |
| RDS PostgreSQL (db.t4g.micro) | **Cloud SQL for PostgreSQL 17, db-f1-micro, 10 GB SSD** | **replace** | See *The database* below. |
| Cognito user pool + Google | **keep on AWS** (Identity Platform = stretch) | **keep** | The API verifies Cognito JWTs itself (JWKS over HTTPS), so it works from any cloud. The only AWS change: the Firebase URL added to the Cognito app client's callback/logout URLs (`infra/auth.tf`, `extra_site_urls`). Moving users to Identity Platform would mean re-registering every user (Cognito cannot export password hashes). |
| EventBridge Scheduler → weekly report | Cloud Scheduler → Cloud Run (stretch) | **keep on AWS** | Reads the AWS database today; moving it means moving the reports bucket and the mailer too. |
| SQS (report queue) | Pub/Sub or Cloud Tasks (stretch) | keep on AWS | goes with the report |
| SES (e-mail) | **no Google service** | **keep SES** | See *E-mail* below. |
| Bedrock (Nova) — agenda parser | Vertex AI Gemini (stretch) | **keep on AWS** | The parser is its own Lambda with a function URL; the site on Firebase calls it as before. |
| SSM / Secrets Manager | **Secret Manager** | replace | The DB password is generated by Terraform and stored only here (6 versions free). |
| CloudWatch Logs | **Cloud Logging** | replace | automatic for Cloud Run |
| IAM roles, OIDC for HCP Terraform | **service accounts, impersonation, no keys** | replace | `terraform@` (only the roles `gcp/` needs, no Owner/Editor) and `spry-api@` (Cloud SQL client + one secret). No JSON key exists: a person runs Terraform with their own `gcloud` login and the providers **impersonate** `terraform@` (short-lived tokens; only that person holds Token Creator on it). For CI the same account would be reached through Workload Identity Federation (GitHub OIDC, condition on the numeric repository ID) — stretch. |
| Terraform `aws` provider, state in HCP Terraform `spry-dev` | Terraform `google` provider, **own state** | replace | Own folder `gcp/`, own state: one plan cannot break both clouds. **Deviation:** the lab asks for a second HCP Terraform workspace; access to the HCP Terraform account was lost (the password-reset e-mail never arrived), so the state is in a **versioned Cloud Storage bucket** (`gcp/bootstrap`). Same guarantees that matter here — separate state, locking, history; what is lost is HCP's run UI and VCS-driven applies. Moving it into a workspace later = a `cloud {}` block + `terraform init -migrate-state`. |
| Region eu-central-1 | **europe-west1 (Belgium)** | — | EU for NFR-7; a Tier 1 region, priced like us-central1 (europe-west3 Frankfurt is ~10–15 % dearer). Firebase Hosting and Cloud Run rewrites support it. |

### The database

| Option | Latency | Bill | Code |
|---|---|---|---|
| **Cloud SQL 24/7** (chosen) | ~1 ms, same region | ≈ $7.7/month instance + $1.70 storage ≈ **$9.40** | none: same PostgreSQL, same Alembic migrations, only `DATABASE_URL` changes (asyncpg over the Cloud SQL unix socket) |
| Cloud SQL, stopped at night | same while on; the first request after a start waits ~1 min | instance hours × $0.0105 + storage $1.70 (e.g. 10 h × 22 days → ≈ $4) | none; but someone (or Cloud Scheduler) has to start/stop it, and a stopped DB = a broken site |
| Firestore | ~10 ms | **$0** at student traffic | the data layer is rewritten: no joins, no foreign keys, no migrations; meetings ↔ participants become duplicated documents |
| Keep RDS on AWS, call it across clouds | +25–40 ms per query (Belgium ↔ Frankfurt over the internet), several queries per request | RDS + public IPv4 + **egress** from both clouds | none, but the DB must be reachable from the internet (public endpoint, TLS, IP allow-list Cloud Run cannot give without a NAT) — a security and latency regression |

**Chosen: Cloud SQL around the clock** for the lab: the code does not change, which is the point
of the exercise (lock-in is in the data layer, not in compute). For a product with no traffic at
night the instance is stopped with `db_activation_policy = "NEVER"` (only storage bills). Firestore
would save ~$9/month at the price of rewriting every query — not worth it while Spry is relational
(meetings, participants, attendance, weekly aggregates).

**Data:** migrations against the empty database (`alembic upgrade head` runs at container start),
no `pg_dump`. The RDS instance is `--no-publicly-accessible` in a private subnet: dumping it would
need a bastion or an ECS one-off task plus an S3 hop, for a few demo rows owned by Cognito users who
exist on both sides anyway. Test data is created again in the UI.

### E-mail

Google Cloud has no e-mail sending service. **Keep SES** (the weekly report already uses it and its
sender identity is verified; a multicloud architecture is allowed). If the report moved to GCP, the
Cloud Run job would call SES with an IAM user's keys — exactly the long-lived key we avoid — so the
better option then is **SendGrid or Mailgun** with the API key in **Secret Manager**, read by the
job's service account only.

### What we would not move

- **Sign-in (Cognito).** Users cannot be migrated with their passwords; Google sign-in users could,
  password users would have to reset. No gain for Spry: Cognito already serves both clouds.
- **The weekly report and the agenda parser,** while the data they read lives where they run: each
  is a self-contained serverless pipeline with its own bucket/queue/model access. Moving them is
  work with no benefit to users.
- **Bedrock → Vertex AI** only if a model is better or cheaper there; the same Claude models exist
  on both, and our trial credit does not pay for partner models.

## Consequences

- Spry's core runs on both clouds from one codebase; the only code change was `--port ${PORT:-8000}`
  in the Dockerfile.
- The GCP copy depends on AWS for sign-in (Cognito JWKS). If AWS is down, nobody can sign in on GCP
  either: the system is multicloud, not cloud-independent.
- Cloud SQL bills ~$0.30/day whether used or not → `terraform destroy` in `gcp/` after grading.
